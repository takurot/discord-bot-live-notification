TwitchとYouTubeのライブ配信通知に特化したDiscord Botの仕様書を作成しました。
副業として収益化（フリーミアムモデル）を前提とした、**「機能差分」**を明確にした設計になっています。

# 配信通知ボット「StreamPulse (仮)」 要件定義書・仕様書

## 1. プロダクト概要
**目的:** 指定されたTwitchおよびYouTubeチャンネルのライブ配信開始を検知し、Discordサーバーの指定チャンネルに自動で通知を行う。
**コアバリュー:** 「推しの配信を見逃さない」環境を提供し、コミュニティの活性化を促す。
**収益モデル:** 基本機能は無料、高度な機能（即時性、カスタマイズ性、登録数）を有料プラン（サブスクリプション）として提供する。

## 2. ターゲットユーザー
* **ストリーマー本人:** 自身のコミュニティ（Discord）へ自動告知したい。
* **ファンコミュニティ運営者:** 「推し」の活動をメンバーと共有したい。
* **eスポーツチーム/クラン:** メンバーの誰かが配信を始めたら通知したい。

## 3. 機能要件

### 3.1 基本機能（無料プラン・有料プラン共通）
* **配信検知:** Twitch, YouTubeの配信開始を検知。
* **自動通知:** 検知後、設定されたテキストチャンネルへメッセージを送信。
* **埋め込み表示 (Embed):** 配信タイトル、配信者名、ゲーム名（カテゴリ）、サムネイル画像、配信URLをリッチなカード形式で表示。
* **オフライン検知:** 配信終了時に通知メッセージを自動更新（例: 「🔴 配信中」→「⚫ 配信終了」）または削除するオプション。

### 3.2 差別化機能（有料プラン向け）
収益化の核となる機能群です。

| 機能 | 無料プラン (Free) | 有料プラン (Pro) |
| :--- | :--- | :--- |
| **登録可能チャンネル数** | 1サーバーにつき **3枠** まで | **無制限** (または50枠など) |
| **検知・通知速度** | ポーリング方式 (5分〜10分遅延) | **Webhook方式 (ほぼリアルタイム)** |
| **メンション機能** | 不可 (通知のみ) | **@everyone, @here, 特定ロール** へのメンション可 |
| **メッセージカスタマイズ** | デフォルトの定型文のみ | メッセージ内容、色、フッターなどを自由に編集可 |
| **複数チャンネル通知** | 1つの通知先のみ設定可 | カテゴリごとに通知先を分けることが可能 |

## 4. 技術スタック・アーキテクチャ案

開発効率とスケーラビリティを考慮した構成です。

* **言語:** Python (discord.py) または Node.js (discord.js)
    * *※非同期処理が得意なNode.js、またはデータ処理ライブラリが豊富なPythonが推奨。*
* **データベース:** PostgreSQL
    * サーバーID、チャンネルID、監視対象の配信者URL、契約プラン状況を管理。
* **インフラ:** AWS (EC2/Lambda) または Google Cloud, Heroku, Railwayなど。
    * *※常時稼働が必要なため、FaaS(Lambda)よりはコンテナ/VPSの方がコスト管理しやすい場合があります。*

### 4.1 API連携仕様
* **Twitch:**
    * **Twitch API (Helix):** ユーザー情報の取得に使用。
    * **EventSub (Webhooks):** 有料プラン向け。Twitch側から通知を受け取るためサーバー負荷が低く、即時性が高い。
* **YouTube:**
    * **YouTube Data API v3:** 正攻法だが、APIの呼び出し回数制限（Quota）が厳しいため注意が必要。
    * **PubSubHubbub (Google):** YouTube公式のプッシュ通知プロトコル。XML形式で通知が来る。API制限を回避しやすく、即時性が高いため推奨。

## 5. データベース設計（簡易ER図イメージ）

* **Servers Table** (導入サーバー情報)
    * `server_id` (PK), `plan_type` (Free/Pro), `joined_at`
* **Streamers Table** (監視対象の配信者マスタ)
    * `streamer_id` (PK), `platform` (Twitch/YouTube), `channel_id`, `last_status` (Live/Offline)
* **Subscriptions Table** (どのサーバーが誰を監視しているか)
    * `id` (PK), `server_id` (FK), `streamer_id` (FK), `notification_channel_id`, `custom_message`, `mention_role_id`

## 6. インターフェース設計（コマンド一覧）

ユーザー体験を向上させるため、最新の「スラッシュコマンド (`/`)」を採用します。

### 一般ユーザー/管理者向け
* `/notify add <platform> <url>`
    * 配信者を監視リストに追加する。
    * 例: `/notify add twitch https://www.twitch.tv/shroud`
* `/notify remove <url>`
    * 監視リストから削除する。
* `/notify list`
    * 現在監視中の配信者一覧を表示する。
* `/notify test`
    * 通知のテスト送信を行う（デザイン確認用）。

### 設定・有料プラン向け
* `/settings message <text>`
    * 通知時のメッセージをカスタマイズする（例: `{streamer}さんが配信を始めたよ！`）。
* `/settings mention <role>`
    * 通知時にメンションするロールを設定する。
* `/upgrade`
    * 有料プランへの案内、決済リンクの表示（Stripe連携などを想定）。

## 💡 開発・運用上の重要ポイント

### 1. YouTube APIの「Quota（割り当て）」問題
YouTube Data APIは無料枠の上限が低いです。多くのユーザーが使うボットになると、すぐに上限に達して機能停止します。
* **対策:** 前述の **PubSubHubbub (RSSベースのプッシュ通知)** を採用するのが定石です。これならばAPIコストをほぼ消費せずにリアルタイム通知が可能です。

### 2. スケーラビリティ
人気ボットになると、数千〜数万サーバーに導入されます。
* **対策:** 「全サーバーの全監視対象を1分ごとにチェックする」ループ処理は、数が多くなるとパンクします。Twitch EventSubやYouTube PubSubHubbubのような「待ち受け型（プッシュ型）」のアーキテクチャを基本に据えることが、サーバーコスト削減と安定稼働の鍵です。

### 3. 次のアクション
もしご自身で開発される場合、まずは**「TwitchのWebhookを受け取って、自分のテストサーバーにメッセージを投げる」**だけの最小構成（MVP）から作り始めることをお勧めします。

これらをベースに開発を進めれば、技術的にもビジネス的にも堅実なボットが作れるはずです。

## 8. 非機能要件（追加）

### 8.1 パフォーマンス・スケーラビリティ
* Proプランでは、配信開始から通知までのレイテンシを**平均30秒以内**（Twitch EventSub / PubSubHubbub依存）を目標とする。
* Freeプランのポーリング間隔は**5〜10分**程度とし、APIクォータとサーバー負荷のバランスを取る。
* 将来的な数千サーバー規模を見据え、Botプロセスはステートレスとし、状態はPostgreSQLなどの外部ストアに集約する。

### 8.2 可用性
* 目標稼働率: **99% / 月**（副業サービスとして現実的なライン）。
* メンテナンス時は、ステータスコマンドや公式Discordサーバーなどを用いて事前周知する。

### 8.3 セキュリティ・プライバシー
* Discord Botトークン、Twitch/YouTube API キーは環境変数またはSecrets Manager等で安全に管理する。
* Webhookには署名検証や検証トークンを用い、不正なリクエストを遮断する。
* 保存する情報は、DiscordサーバーID・チャンネルID・配信者情報など、サービス提供に必要な最小限にとどめる。

### 8.4 ログ・監視
* 通知成功数・失敗数、APIエラー数、配信検知レイテンシなどのメトリクスを収集し、ダッシュボードで可視化する。
* 致命的なエラーやWebhook障害発生時には、開発者向けDiscordサーバーやメールにアラートを送信する。

## 9. プラン設計の補足

### 9.1 Freeプラン
* 登録可能チャンネル数: 1サーバーあたり最大3枠（Twitch/YouTube合算）。
* 検知方式: ポーリング方式（5〜10分間隔）。
* 通知内容: デフォルトテンプレートのみ、メンションなし。

### 9.2 Proプラン
* 登録可能チャンネル数: 実質無制限（システム保護のため上限50〜100枠程度を想定）。
* 検知方式: Webhook/EventSub/PubSubHubbubによるプッシュ型（ほぼリアルタイム）。
* 通知内容: メンション（@everyone/@here/特定ロール）、Embedの色・文言・フッター等をカスタマイズ可能。
* 課金: 月額サブスクリプション（Stripeなどの決済基盤と連携）を想定。

## 10. MVP範囲（最初に実装するスコープ）

1. **対応範囲の限定**
    * まずは Twitch のみ対応（YouTube対応は後続フェーズ）。
    * Freeプランのポーリング方式での配信検知から開始し、Pro向けのWebhook対応は第2フェーズとする。
2. **最低限の機能セット**
    * `/notify add/remove/list/test` の実装。
    * Twitch API を用いた配信開始検知 + Discord Embed での通知。
    * Servers / Streamers / Subscriptions の最小限スキーマを実装。
3. **運用・監視まわり**
    * ログ出力と最低限のエラーハンドリング。
    * シンプルな `/status` コマンド（Botの稼働/応答状況を返す）を提供。

このMVPが安定稼働した段階で、YouTube対応・Proプラン（Webhook化）・高度なカスタマイズ機能・Webダッシュボードなどを順次追加していく方針とします。
